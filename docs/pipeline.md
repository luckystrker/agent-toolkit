# Пайплайн разработки

Как компоненты тулкита работают вместе, от идеи до коммита. Harness-agnostic:
одни и те же скиллы и гейт работают в Claude Code, ZCode, Codex, OpenCode, Pi,
Antigravity, Qoder, Devin (см. матрицу в README).

## Карта

```
        требования размыты
              │
              ▼
        ┌───────────┐   фиксирует решения, а не разговор
        │ grilling  │   (один вопрос за раз, варианты, граница знания)
        └─────┬─────┘
              ▼
     ┌──────────────────┐   этапы, зависимости, параллелизуемость,
     │ spec-to-checklist │   критерии Г (гейты) / Р (ручная приёмка)
     └────────┬─────────┘
              ▼
        реализация ──── tdd (справочник качества тестов: швы, антипаттерны)
              │
              ▼
     ┌───────────┐    тестировщик (PBT + краевые, ПО СПЕКЕ)
     │acceptance │ →  критик (мутации с прогоном и откатом, ≥80%)  ← цикл ≤ 3 итераций
     └─────┬─────┘    гейт: lint/typecheck/test зелёные
              │
              ▼
        git commit ──── гейт-хук (то же самое, принудительно)
              │          сообщение: CHECKLIST N.N — <что сделано>
              ▼
     handoff (конец сессии: сделано / где остановился / следующий шаг)
```

Параллельно, по необходимости: `research` (первоисточники со ссылками),
`code-review` (ревью большого диффа от точки, две оси: стандарты/спека).

## Правила, которые держат конвейер

1. **Гриллинг до кода.** Стоимость ошибки в разговоре — минуты, в коде — часы.
   Каждый вопрос с вариантами и рекомендацией; граница знания фиксируется
   как «принято по умолчанию», а не прячется.
2. **Двухуровневая готовность.** «Г» (гейты зелёные) ≠ «Р» (пользователь
   увидел живой прогон). Этап не закрыт без обоих.
3. **Зелёные тесты исполнителя не принимаются.** Тесты пишет отдельная роль,
   атакует их отдельная роль; мутации исполняются (применил → прогнал →
   откатил), выжившая мутация = дыра, а не «наверное ок».
4. **Гейт перед каждым коммитом.** Хук блокирует commit при красном
   lint/typecheck/test и при расхождении дерева с индексом — правило
   Enforcement, не договорённость.
5. **Связность против дрейфа.** Отметка `[x]` в чек-листе — в том же коммите;
   сообщение коммита — `CHECKLIST N.N — <что>`; отчёт приёмки — в
   `docs/acceptance/`, ссылкой из пункта; изменение решения — записью в
   «Изменения решений» с датой и причиной; новое требование — в бэклог,
   не молча в код.
6. **Сессия заканчивается handoff'ом.** Свежая сессия не имеет контекста:
   «где именно остановился» с точностью до файла, а не «почти готово».

Эти шесть правил доставляются в контекст агента секцией-диспетчером в
AGENTS.md (`agents/pipeline-section.md`) — конвейер существует не только в
документации, но и в рабочем контексте каждого harness'а.

## Роли в цикле приёмки (скилл acceptance)

| Роль | Контекст | Задача |
|---|---|---|
| Исполнитель | вся сессия | код; тесты не пишет |
| Тестировщик | свежий субагент | тесты по спецификации: PBT, границы, «нет — так нет» |
| Критик | свежий субагент | атакует тесты: мутации с фактическим прогоном и откатом, тавтологии, покрытие |
| Ведущая сессия | ты | арбитр ≤3 циклов, перепроверка выживших мутаций |

Harness без субагентов — роли идут последовательными проходами с явной сменой
роли; в отчёте приёмки это помечается как понижение гарантий (изоляции нет).

## Применимость

Пайплайн генеричен: спецификация/чек-лист могут быть любыми (PRD, архитектура,
тикет, spec.md). Стек-специфично только содержимое гейтов — сейчас это
npm-скрипты `lint`/`typecheck`/`test` проекта.
