# Когда мокать

Мокать только на **границах системы**:

- Внешние API (платежи, почта и т.п.)
- Базы данных (иногда — предпочитай тестовую БД)
- Время / случайность
- Файловая система (иногда)

Не мокать:

- Собственные классы/модули
- Внутренних участников
- Всё, что ты контролируешь сам

## Проектирование под мокаемость

На границах системы делай интерфейсы, удобные для мокания:

**1. Внедряй зависимости**

Внешние зависимости передавай снаружи, а не создавай внутри:

```typescript
// Легко мокать
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total);
}

// Трудно мокать
function processPayment(order) {
  const client = new StripeClient(process.env.STRIPE_KEY);
  return client.charge(order.total);
}
```

**2. SDK-стиль вместо генерических загрузчиков**

Отдельная функция на каждую внешнюю операцию вместо одной общей с условной логикой:

```typescript
// ХОРОШО: каждая функция мокается независимо
const api = {
  getUser: (id) => fetch(`/users/${id}`),
  getOrders: (userId) => fetch(`/users/${userId}/orders`),
  createOrder: (data) => fetch('/orders', { method: 'POST', body: data }),
};

// ПЛОХО: мок требует условной логики внутри мока
const api = {
  fetch: (endpoint, options) => fetch(endpoint, options),
};
```

Что даёт SDK-подход:

- Каждый мок возвращает одну конкретную форму
- Нет условной логики в подготовке теста
- Видно, какие операции трогает тест
- Типобезопасность на операцию
