# Разработка через тесты (TDD)

TDD — цикл «красный → зелёный»: сначала тест, который падает, потом минимальный код, который его зажигает. Скилл — справочник, который делает этот цикл производительным: каким должен быть хороший тест, где он живёт, антипаттерны и правила цикла. Каждый раздел применяется на каждом витке: сверяйся до и во время, не после.

Изучая кодовую базу, прочитай `GLOSSARY.md` проекта (если есть), чтобы имена тестов и vocabulary совпадали с доменном проекта.

## Каким должен быть хороший тест

Тесты проверяют **поведение через публичные интерфейсы**, а не внутренности. Код может полностью измениться — тесты не должны. Хороший тест читается как спецификация: «пользователь может оформить заказ с валидной корзиной» говорит, какая возможность существует, и переживает рефакторинг, потому что ему всё равно на внутреннюю структуру.

Примеры хороших/плохих тестов — [tests.md](tests.md), правила моков — [mocking.md](mocking.md).

## Швы: где живут тесты

**Шов (seam)** — публичная граница, на которой ты наблюдаешь поведение, не залезая внутрь. Тесты пишутся на швах, никогда — против внутренностей.

**Тестировать только на согласованных швах.** До написания первого теста выпиши швы под тест и подтверди их у пользователя. Тест на несогласованном шве не пишется. Всех швов не покрыть — предварительное согласование и есть способ уложить усилия на критичные пути и сложную логику, а не на каждый пограничный случай.

Спроси: «Какой публичный интерфейс, и какие швы проверяем?» Каждому предлагаемому шву — строка: что ловит и чего не видит.

Мини-словарик шовов: **модуль** — часть кода со своим интерфейсом; **глубина** — сколько внутренностей модуль скрывает за простым интерфейсом (глубже = лучше); **адаптер** — тонкая обёртка над внешней системой, единственное место, где она касается кода; **шов** — граница модуля или адаптера, пригодная для наблюдения поведения в тесте.

## Антипаттерны

- **Привязка к реализации**: мокает внутренних участников, тестирует приватные методы или проверяет через обходной канал (запрос в базу вместо интерфейса). Примета: тест падает при рефакторинге, хотя поведение не изменилось.
- **Тавтологичность**: ожидаемое значение вычисляется тем же способом, что и в коде (`expect(add(a, b)).toBe(a + b)`) — тест зелёный по построению и никогда не разойдётся с кодом. Ожидаемые значения берутся из независимого источника истины: известный литерал, прорешанный пример, спецификация.
- **Горизонтальная нарезка**: сначала все тесты, потом вся реализация. Групповые тесты проверяют *воображаемое* поведение — форму вещей, а не поведение для пользователя, и теряют чувствительность к реальным изменениям. Работай **вертикальными срезами**: один тест → одна реализация → повтор; каждый тест — **трассирующий снаряд**, отвечающий на то, чему научил предыдущий виток.

## Правила цикла

- **Красный прежде зелёного.** Сначала падающий тест, потом ровно столько кода, чтобы его зажечь. Не предвосхищать будущие тесты, не добавлять умозрительные возможности.
- **Один срез за раз.** Один шов, один тест, одна минимальная реализация за виток.
- **Рефакторинг — не часть цикла.** Он принадлежит стадии ревью (скилл `code-review`), а не витку «красный → зелёный».
