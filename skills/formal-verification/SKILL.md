# Инварианты до кода

Тесты проверяют сценарии, которые кто-то придумал. Модель-чекер перебирает **все** чередования шагов в маленьком мире и находит то, что не придумал никто: двойное списание при повторе запроса, потерю записи при гонке двух процессов. Для фич с деньгами, данными и конкурентностью **без формальной проверки код не принимается** — это часть финишной черты.

## 1. Инварианты словами

Из спеки (раздел «Инварианты») или гриллинга. Каждый — одна фраза, которую поймёт владелец: «сумма по всем счетам не меняется при переводе», «заказ не оплачивается дважды, даже если клиент нажал два раза». Покажи список пользователю: это то, что будет доказано, — и то, что НЕ будет (за пределами модели).

## 2. Модель TLA+

Опиши **протокол, а не код**: состояния, шаги (в том числе сбои, повторы, параллельные процессы), инварианты. Маленькие константы (2 процесса, 3 запроса) — TLC перебирает всё. Файлы: `spec/tla/<Имя>.tla` + `<Имя>.cfg`.

```tla
---------------------------- MODULE Transfer ----------------------------
EXTENDS Naturals
CONSTANT Total
VARIABLES a, b, inflight
vars == <<a, b, inflight>>

Init     == a = Total /\ b = 0 /\ inflight = 0
Withdraw == a > 0 /\ inflight = 0 /\ a' = a - 1 /\ inflight' = 1 /\ UNCHANGED b
Deposit  == inflight = 1 /\ b' = b + 1 /\ inflight' = 0 /\ UNCHANGED a
Next     == Withdraw \/ Deposit
Spec     == Init /\ [][Next]_vars

MoneyConserved == a + b + inflight = Total
=========================================================================
```

```
\* Transfer.cfg
CONSTANT Total = 3
SPECIFICATION Spec
INVARIANT MoneyConserved
\* все деньги переведены — шагов больше нет; это нормальный конец, а не зависание
CHECK_DEADLOCK FALSE
```

`CHECK_DEADLOCK FALSE` ставь, только если остановка — законный конец протокола (как здесь). Если система по замыслу работает бесконечно (очередь, сервер), deadlock — настоящая находка: оставь проверку включённой.

Запуск: `node <bin>/tlc.mjs` (все модели `spec/tla/`) или `node <bin>/tlc.mjs spec/tla/Transfer.tla`; java и `tla2tools.jar` (`~/.agent-toolkit/tla/`, ставит установщик) скрипт находит сам. Ненулевой код выхода = находка: нарушен инвариант (трасса в выводе), зависание (deadlock) или ошибка в модели (`tla2tools.jar` — релизы github.com/tlaplus/tlaplus; нужна Java 11+). Нет Java — скажи пользователю и предложи поставить; не подменяй модель рассуждением.

## 3. Мутанты краснеют

Модель, которая никогда не краснеет, ничего не доказывает. Сделай 2–3 мутации **модели** — убери защиту, которая по замыслу держит инвариант (в примере: в `Deposit` не сбрасывать `inflight` → повторное зачисление). TLC **обязан** найти нарушение и показать трассу. Мутация выжила → инвариант сформулирован слишком слабо или модель не описывает опасный шаг; чини модель, не мутацию. Результаты (мутация → нарушенный инвариант → длина трассы) — в отчёт.

## 4. Тест на живом коде

Каждый инвариант модели → property-based тест на реальном коде (fast-check / hypothesis / proptest): генерируются последовательности операций, включая повторы и сбои, после каждой — проверка инварианта. Трассы-контрпримеры из шага 3 становятся фиксированными регрессионными тестами. Модель доказывает дизайн, тест — что код ему соответствует; одно без другого не принимается.

## 5. TLC в поезде

Проверка модели — гейт, а не разовая акция, и включать её не нужно: **каждая модель в `spec/tla/` (файл `<Имя>.tla` с `<Имя>.cfg` рядом) проверяется TLC перед каждым коммитом автоматически** — гейт находит модели сам. Модуль без `.cfg` считается вспомогательным (его подключают через `EXTENDS`). Нет java или `tla2tools.jar` — коммит блокируется, а не проходит непроверенным.

Свой способ запуска (другие флаги, Apalache) — гейт `tlc` в `.agents/gate.json` или npm-скрипт `tlc`: тогда автопроверка уступает ему. Модель большая и не укладывается в таймаут гейта (120 с) — уменьши константы или подними `timeoutSec` в `.agents/gate.json`.

Код протокола поменялся, а модель нет — это находка ревью (ось «Спека»).

## Отчёт
