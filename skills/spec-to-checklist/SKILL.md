# Спека → чек-лист этапов

Превращает спецификацию в рабочий документ против дрейфа: сделал шаг — отметь. Само исполнение по чек-листу тривиально; вся ценность — в правильной нарезке.

## Вход

Найди документ спецификации (по AGENTS.md проекта, по прямому указанию, либо спроси). Прочитай целиком до нарезки. Если в спеке дыры — сначала предложи гриллинг по ним, не выдумывай недостающее.

## Правила нарезки

1. **Этапы = параллелизуемые части** где это возможно (инфраструктура, схема данных, ядро, модули, UI — могут идти параллельно, если не зависят). Явно указывай «Зависит от: N» и «Параллелизуем с: M».
2. Каждый пункт чек-листа **атомарен и проверяем**: по нему можно однозначно сказать «сделано» после одной фокусированной задачи.
3. Ничего сверх спецификации. Идеи, всплывшие при чтении, — отдельным списком «вопросы к спецификации», не в этапы.
4. **Двухуровневый критерий готовности этапа** (оба обязательны, это разные вещи):
   - **Г (технически готово):** какие тесты/гейты должны быть зелёными.
   - **Р (готово к ручной приёмке):** какой реальный прогон пользователь сможет увидеть/проделать руками.
5. Структура файла чек-листа: сверху секция «Изменения решений» (пустой шаблон комментария), затем этапы, внизу «Бэклог».

## Выход

`CHECKLIST.md` в корне проекта (или обновление существующего — тогда только добавь/уточни этапы, не перетряхивай принятые отметки без вопроса). После создания — короткое резюме: сколько этапов, что параллелится, какие вопросы к спецификации остались.

## Против дрейфа (памятка в конец файла)

- Новое требование → в бэклог или в конец чек-листа, не молча в код.
- Изменение принятого решения → комментарий в начале файла: дата, что изменилось, почему.
- Отметка `[x]` ставится в том же коммите, что и работа по пункту.
- Сообщение этого коммита ссылается на пункт: `CHECKLIST N.N — <что сделано>`; туда же — ссылка на отчёт приёмки из `docs/acceptance/`, если цикл приёмки прогонялся (ревью по этому правилу ищет происхождение работы).
