# Цикл приёмки кода

Защита от главного обмана: «зелёные тесты», написанные тем же исполнителем под его же код. Тесты пишет отдельная роль, и их атакует отдельная роль.

## Роли и изоляция

Каждая роль — **свежий контекст**, отдельный субагент, если harness их умеет (Task/Agent — как инструмент субагентов называется в текущем harness). Критик не должен видеть переписку тестировщика: ему передаются код, дифф, спецификация и готовые тесты — без хода их создания, иначе он «пропитается» логикой исполнителя и пропустит подгонку.

Harness без субагентов — роли идут последовательными проходами в одном контексте с явной сменой роли («сейчас я тестировщик», «теперь я критик»). Это слабее: изоляции нет. В таком режиме обязательно пометь в отчёте «изоляция контекстов не достигнута — гарантии понижены».

- **Тестировщик** — пишет тесты ПО СПЕЦИФИКАЦИИ, не по коду: property-based (fast-check для TS, hypothesis для Python, proptest для Rust — что найдётся в проекте) + краевые случаи из чек-листа/спеки. Не подглядывать в реализацию «как удобно».
- **Критик** — атакует тесты тестировщика, не код: покрытие диффа ≥ 80%; подгонка под реализацию; пропущенные краевые случаи; asserts, которые всегда истинны.

## Цикл

1. Собери контекст: дифф/изменённые файлы, пункт чек-листа, раздел спецификации, **список согласованных швов** (см. скилл tdd; если швы не согласованы — согласуй с пользователем до старта).
2. **Тестировщик** пишет тесты по шаблону промпта ниже и прогоняет. Красные тесты = находки, не «почини под код» (если код не соответствует спеке — это баг кода).
3. **Критик** ревьюит тесты по шаблону ниже. Замечания → обратно тестировщику.
4. Цикл ≤ **3 итераций**. Не сошлись — стоп, докладывай спор пользователю с позициями сторон.
5. **Гейт:** линтер + проверка типов + юнит-тесты зелёные (те же команды, что в гейт-хуке проекта, если он есть).
6. **Зелёные тесты тестировщика без вердикта критика не принимаются никогда.**

## Мутации исполняются, а не предлагаются

Вердикт критика обязан опираться на **фактически прогнанные** мутации. Рассуждение «эта мутация наверняка уронит тест» — самооценка, она не считается. Протокол для каждой из 2–3 точечных мутаций:

1. Примени мутацию к коду (например, поменять границу сравнения, инвертировать условие, выкинуть ветку).
2. Прогони тесты: `npm test` (или аналог проекта). Мутация **обязана уронить хотя бы один тест**.
3. Откат точно: `git checkout -- <файл>` (или восстанови байты вручную, если вне git). Убедись, что дерево чистое (`git status`).
4. Запиши результат в отчёт: мутация → какой тест упал → откачено.

**Выжившая мутация = дыра в покрытии**, а не «наверное ок». Она либо закрывается новым тестом тестировщика, либо попадает в отчёт как известная дыра.

## Шаблоны промптов ролей

Передаются дословно; `{{...}}` заполняешь перед запуском.

**Тестировщику** (субагент с полными инструментами):

> Ты — тестировщик. Тебе даны: спецификация ({{раздел}}), дифф ({{команда или содержимое}}), согласованные швы ({{список: что тестируем, куда не лезем}}). Пиши тесты ПО СПЕЦИФИКАЦИИ, через публичные интерфейсы из списка швов, не подглядывая в реализацию: property-based, если в проекте есть библиотека, плюс краевые случаи. Красный тест = находка, не повод подгонять ожидание под код. Отчитайся: файлы тестов, что покрывает каждый, какие требования спеки остались непокрытыми и почему. Не правь код.

**Критику** (субагент; тестировщику запрещено объяснять свои решения):

> Ты — критик, атакуешь тесты, не код. Даны: спецификация ({{раздел}}), дифф ({{...}}), тесты тестировщика ({{файлы}}). Проверь: (a) покрытие диффа ≥ 80% — где меньше; (b) тавтологии — asserts, истинные всегда; (c) подгонку под реализацию — тесты, проверяющие «как сделано» вместо «что требуется»; (d) пропущенные краевые случаи. Затем выбери 2–3 точечные мутации кода и исполни каждую по протоколу: применил → прогнал тесты → откатил (`git checkout -- <файл>`), с выводом команд в отчёте. Выжившая мутация = дыра. Отчитайся: находки списком, мутации с результатами прогонов. До 400 слов.

## Отчёт «готово к ручной приёмке» — файл, не чат

После цикла сохрани отчёт в **`docs/acceptance/{{этап-или-slug}}.md`**:

- **Проверено:** чем и как (тесты, покрытие, мутации с результатами прогонов, гейты).
- **Не проверено:** что осталось за рамками автоматизации.
- **Как проверить руками:** конкретная команда/шаги и ожидаемый наблюдаемый результат.
- **Оговорки:** известные шероховатости, допущения; отметка, если изоляция ролей не достигнута.

Затем: ссылка на отчёт — в пункт чек-листа; отметка `[x]` и отчёт уходят **в том же коммите**, сообщение коммита — `CHECKLIST N.N — {{что сделано}}`. Только после этого — коммит (гейт-хук догонит, если что забыл; для PreToolUse-адаптера остаточный риск: обёртка-скрипт с `git commit` внутри — базовое принуждение держит git-хук).
